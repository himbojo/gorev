# Technical Retrospective: gorev v1.0.0-beta

## Overview
This retrospective covers the development of `gorev` up to the `v1.0.0-beta` milestone. The goal was to build a high-performance, lightweight OCSP responder and CRL server with Redis-backed state management.

## Successes

### 1. Robust Multi-CA Support
The implementation successfully handles multiple Certificate Authorities by strictly matching issuer information from OCSP requests. The use of a `multiDirHandler` ensures that we can serve CRLs and CA certs from a unified directory structure while maintaining security boundaries.

### 2. High-Performance Caching
Integrating Redis for OCSP response caching has significantly reduced cryptographic overhead. The atomic cache invalidation logic ensures consistency during PKI reloads without sacrificing performance.

### 3. Asynchronous Observability
The `fsnotify` implementation with a 2-second debounce provides a seamless "hot-reload" experience for operations. Administrators can simply drop new PEM/CRL files into the data directory, and the system automatically reconciles the state.

### 4. Comprehensive E2E Testing
The `scripts/test_e2e.sh` and `stress_test.go` provide high confidence in the system's stability. Being able to simulate 1 million revocations ensures the system is ready for enterprise-scale CRLs.

## Challenges & Implementation Choices

### 1. Security vs. Flexibility in HTTP Routing
We chose a flexible endpoint configuration (`ENDPOINTS_*` env vars) to support various deployment patterns. This introduced complexity in the `multiDirHandler`. We prioritized security by implementing strict symlink resolution and path validation to prevent traversal attacks.

### 2. CRL Validation
Initially, CRLs were loaded without verification. We pivoted to require signature verification against the issuing CA before loading revocations into Redis. This adds a critical layer of integrity but requires the corresponding CA certificate to be present in the `cas/` directory.

### 3. PEM-only Strategy
We intentionally moved away from PFX support to avoid hardcoded passwords in configuration or service files. This enforces better security practices by relying on standard PEM-encoded keys and certificates managed via file-level permissions.

## Technical Debt & Future Considerations

### 1. Metrics & Monitoring
Currently, monitoring is limited to logs. Future iterations should include a `/metrics` endpoint for Prometheus to track cache hit ratios, OCSP response latencies, and file-watcher events.

### 2. HSM Integration
For production environments, signing OCSP responses with private keys stored on disk is a risk. We should investigate `PKCS#11` support for Hardware Security Modules (HSMs).

### 3. Redis High Availability
The current setup uses a single Redis instance. For mission-critical PKI, we should document or implement support for Redis Sentinel or Cluster modes to ensure high availability.

### 4. OCSP Nonce Support
Full RFC 6960 nonce support should be reviewed to ensure we are correctly handling requestors that require nonce reflection for replay protection.
